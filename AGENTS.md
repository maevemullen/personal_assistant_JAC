# Working in this Jac project

This is a [Jac](https://www.jaseci.org/) project. Jac's syntax has evolved and
is easily confused with Python or JSX -- before writing or editing `.jac`
files, consult the reference guides bundled with the compiler.

## Reference guides

The `jac` CLI ships curated reference guides ("Agent Skills") -- versioned
coding guidance for the installed compiler:

- `jac guide` -- list every available guide
- `jac guide <name>` -- print a guide (e.g. `jac guide jac-types`)
- `jac guide --search <keyword>` -- find guides by topic
- `jac guide --json` -- machine-readable output for tooling

Start with `jac guide jac-essentials`, then load the guide for your task.
Use `jac guide <name> --sections` to list headings and
`jac guide <name> --section <slug>` to retrieve a relevant section.

## Validate your work

- `jac check <file>` -- type-check and lint. Compiler diagnostics link to the
  relevant guide; follow the `-> run 'jac guide ...'` hints.
- `jac run <file>` -- execute a Jac script.
- `jac run --dev main.jac` -- serve a web-app or service in dev mode
  (hot-reload for client files; restart for server changes). Use this instead
  of `jac run` for apps.
- `jac browse <action>` -- QA a running app in a headless browser:
  `jac browse open localhost:8000`, then `snapshot` (accessibility tree with
  `@e1`-style refs), `click @e5`, `fill '#email' user@example.com`, `screenshot`, `close`.

_Generated by `jac create`._

## Project: personal planning app (course assignment, due Mon Oct 5, 2026)

An individual course project: a personal planner built in Jac with four
components that share one backend and one set of planning data.

1. Server -- planning logic, data persists between sessions
2. Web frontend -- browser interface for managing plans
3. Mobile app -- mobile interface connected to the same backend
4. CLI -- terminal commands for useful planning actions

Each component must have working functionality. A small, polished,
reliable tool beats a long list of unfinished features.

## Hard requirements (do not break these)

- From a fresh checkout, `jac run` at the repo root must start the web app
  and its server. Configure the default app in `jac.toml` accordingly.
- All four components are written in Jac and talk to the same server.
- Root-level `README.md` must contain: name and UMID, a brief description
  and main features, setup and run instructions (prerequisites, config),
  how to launch and use the mobile app and the CLI, and a short explanation
  of how the four components fit together and what makes it impressive.
- Anything needing extra setup (mobile platform tools, API keys) must be documented in the README.
- README prerequisites must include the Jac install command, the
  `jac --version` check, and any model setup (`jac install 'byllm[local]'`
  and the first-run download, or the API key variable for a cloud model).

## Decisions (edit these)

- Use case: Coursework deadlines plus a daily task listgit remote add origin
- Users: single user, no login
- Task fields: title, due date, priority, category, progress status, energy needed to complete, 
- Core actions: add, view today, mark complete, edit, delete
- Web: plan and edit the full week
- Mobile: view today's tasks and mark them complete
- CLI: quick
- AI feature: auto-categorize a new task with `by llm()`, using the local
  Gemma model (`jac install 'byllm[local]'`). If the model is unavailable
  or slow, fall back to a category the user picks; never crash or block
  adding a task.
- Out of scope: login and per-user data (tutorial Part 6), the tutorial's
  meal shopping list, recurring tasks, reminders

## How to work

- Do not guess Jac syntax from Python or JSX habits. Check `jac guide` or
  the example workspace first.
- Put shared planning logic in one common core; the web, mobile, and CLI
  call it rather than reimplementing it.
- Build in vertical slices: get one action (add a task) working across
  server, web, mobile, and CLI before starting the next action.
- After each change, run `jac check` on the files touched and fix all
  diagnostics. Use `jac browse` to verify web changes in a running app.
- Commit after each working slice with a clear message.
- Ask before adding dependencies, changing the project structure, or
  expanding scope beyond the Decisions section.
- If something cannot be verified (e.g. the mobile app on a real device),
  say so plainly instead of assuming it works.
- Keep the README current as commands and setup steps change.

## Tutorial reference

The "Build an AI Day Planner" tutorial is the starting pattern for the
server and web frontend:
https://jaclang.org/docs/v0.37/tutorials/first-app/build-ai-day-planner

- Parts 2-3: tasks are `node`s connected to `root`; the graph is the
  persistence layer, so do not add a separate database. Expose backend
  functions with `def:pub`; identify nodes with `jid()`.
- Part 4: web frontend with client-side code, JSX, and reactive `has`
  state, importing server functions directly.
- Part 5: AI with `by llm()`, `obj`, and `sem` for structured output.
- Part 6 (auth) is out of scope. Part 7 (walkers) is optional; use plain
  functions unless a walker is clearly simpler.
- The tutorial does not cover mobile or CLI. Take those patterns from the
  example workspace.
- Run `jac --version` first. If the tutorial or web docs disagree with
  `jac guide` for the installed version, trust `jac guide`.

## Definition of done

- Fresh clone, documented setup, then `jac run` starts web and server.
- A task added in any one interface shows up in the other two.
- Data survives a server restart.
- README instructions have been followed step by step and work.
